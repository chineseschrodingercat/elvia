# Problem 1: the displayed Verus specification already preserves prior elements

Source claim and location. Appendix D.2.3, p. 50, in the boxed Verus example, identifies failure to preserve the original ring-buffer elements as an omitted postcondition. The same box displays the branch-sensitive whole-sequence relation below. The source page was visually inspected. [E1, E5-E6]

Code:
if ret {
    self.view() === old(self).view().push(val)
} else {
    self.view() === old(self).view()
}

Complete analytic check. Let q be the old logical sequence, q’ the post-state sequence, and n the length of q. If ret is true, the displayed clause gives q’ = q.push(val). By the indexed definition of sequence append, q’[i] = q[i] for every integer i with 0 <= i < n; q’ has length n+1 and its last element is val. If ret is false, the clause gives q’ = q, so every previous element is again retained. These are the only two Boolean branches. Thus the exact omission alleged in the prose is already excluded by the displayed postcondition.

\[\forall\,i\in\mathbb{Z},\quad 0\le i<|q|\ \Longrightarrow\ q'_i=q_i.\] Assumptions and independent source check. In the linked prepublication implementation, View for RingBuffer<T> has V = Seq<T>; its view enumerates the stored elements from head to tail modulo capacity. The inspected implementation also writes preservation as an explicit indexed equality in its enqueue contract. The two formulations agree on this property. This is a semantic argument about the printed contract, not a claim that the printed implementation was mechanically verified, or that all necessary preconditions are printed in the box.

Alternative readings and counterevidence. A different, unfaithful view abstraction could make a postcondition irrelevant to physical contents; the linked view explicitly maps to the active stored elements, so that escape does not explain this example. A client using only a weaker trait-level contract may know less, but that is different from the concrete contract shown in the paper. The box could still omit other requirements, including a particular capacity policy; this review does not assert complete specification adequacy. The precise preservation accusation fails.

Impact and repair status. The example does not demonstrate the stated autoformalization failure. This is a local defect in evidence supporting D.2.3’s recommendation to refine specifications interactively. No downstream theorem or quantitative result depends on the alleged omission, and the separate argument that formal specifications can fail to capture intent is not contradicted. Remove or replace this example, or explicitly discuss a genuinely missing property. The preservation implication is analytically verified; a replacement example and its model provenance are not verified. Supported judgment: Minor.

# Problem 2: the Astropy example reverses the issue’s explicit request

Source claim and location. Appendix C.3, p. 38, in the serializer-deserializer box, describes astropy #14181 as requesting a new reStructuredText input format, treats writing as an implicit requirement, and reports that models implemented only reading. The source page was visually inspected. [E1, E3-E4]

Complete source comparison. The primary issue is titled ’Please support header rows in RestructuredText output’. Its reproducer first successfully calls tbl.write with format=’ascii.rst’, then requests header_rows for that same output format. The failure is an unexpected header_rows argument. Output is therefore explicit, and basic support for the format already exists. This does not match either the claimed input direction or the claimed introduction of a new format.

PR #14182 strengthens and limits the conclusion. Its patch adds configurable header rows and adjusts both read and write paths, with a round-trip test. Consequently the example may have a repairable directional reversal: reading may be the implicit companion to an explicitly requested writing feature. That possibility is counterevidence to any claim that the broad serializer-deserializer principle itself fails.

Unresolved model provenance. The issue and human-authored PR establish what was requested and repaired. They do not identify the exact model, prompt, patch or evaluation run underlying the paper’s behavioral allegation. This review does not infer whether a published model implemented only read, only write, or both. A mistaken issue identifier or reversed narration could explain the discrepancy, but neither is demonstrated.

Impact and precise supported correction. Correct the description to an explicit request for header-row support in an existing reStructuredText output writer. That textual correction is supported by the primary issue. It does not by itself restore the alleged model-failure example; that requires the actual evaluation patch and a faithful comparison with the request. The existing narration cannot support an inference about missing implicit writing behavior. This bounded evidentiary defect is Minor; the unverified model behavior remains Needs Evidence and does not raise the paper’s supported severity.

# Other checks, counterevidence, and dependency assessment

The appendix’s p. 33 square-invariant example depends on integer semantics: mathematical integers, checked/no-overflow executions and fixed-width wraparound integers differ. Because the paper does not identify the language or integer model, this was retained as a scope clarification rather than promoted into a demonstrated counterexample satisfying its operative assumptions.

The p. 35 CompCert description must be understood within the verified compiler transformations and trusted components. No central claim was rejected solely for compressed overview wording. The p. 4 Qwen language-accuracy comparison was investigated against the cited technical report, but the exact size/version and D-language comparison were not independently resolved; it remains an evidence limitation, not a demonstrated numerical error. The p. 9 SWE-bench progress comparison was not reconstructed to a common subset and evaluation configuration.

The dependency of the confirmed defects is specific: the p. 50 box supports the discussion of incomplete formalizations in D.2.3; the p. 38 box supports the discussion of implicit requirements in C.3. Neither supports a new claimed theorem or a measured effect size, and neither is the only premise offered for the paper’s task taxonomy or proposed research directions. The findings therefore concern two examples. Other examples and citations have only the coverage described in the ledger; their survival is not a proof that all of them are correct.

Version check. The publisher-linked PDF is the review target. A related arXiv record, 2503.22625v1, dated 28 March 2025, has a different title, a 75-page scope and additional authors; it was not silently substituted for this 61-page conference version. Publisher and related-version metadata were checked. OpenReview’s direct web page presented a browser-verification wall, so its full discussion and revision history were not inspected. No claim of an exhaustive erratum search or verified later repair is made.
