# 2. Problem 1 (Minor): the baseline OIDC UserInfo flow uses the wrong token

Location and claim. At the transition from p.4 to p.5, Section 3.1 describes ordinary OIDC as letting a merchant submit an ID token to an OP token-validation endpoint to obtain further user information. This conflates ID-token validation with retrieval of claims through UserInfo.

Primary standard. OpenID Connect Core 1.0 incorporating errata set 2 (15 December 2023), Sections 5.3 and 5.3.1, specifies UserInfo access using an Access Token. Section 3.1.3.7 separately specifies ID-token validation. These provisions do not require a generic endpoint that turns an ID token into a UserInfo request.

Concrete standards-level witness. Consider a conforming provider that issues an ID token I and a distinct access token A to registered client C. Its UserInfo endpoint recognizes A as an access credential and rejects I as an invalid access credential. C can still validate I and obtain UserInfo using A. This provider implements the standard yet does not implement the manuscript’s claimed ID-token exchange. This is an analytic protocol comparison; no live provider, real account or token request was used.

Operation | Credential and responsibility

Validate the user’s authentication result | The relying party validates the ID token according to OIDC rules.

Request additional user claims | The client presents the appropriate Access Token to UserInfo.

Validate the proposed agent delegation | The new credential and verification service require an explicit extension/profile; this behavior does not follow merely from OIDC Core support.

Strongest alternative reading. A particular provider may expose a nonstandard tokeninfo or introspection service. Section 3.2 also explicitly proposes custom registration and newly introduced delegation credentials, so the authors can define additional endpoints. These possibilities preserve the broader design direction but do not make the described background behavior part of ordinary OIDC Core.

Impact and severity. Minor: Section 3.1 incorrectly substitutes an ID token for the access credential used by UserInfo. Section 3.2 instead proposes customized registration and new delegation credentials; Figure 2 explicitly adds delegation mechanisms. Its identity-and-scope architecture does not require the erroneous baseline exchange. ’Standard OP’ therefore needs qualification as an appropriately extended provider with a defined credential-validation profile; ordinary OIDC Core support does not supply that profile. No specific authentication or non-escalation inference in the customized design depends on ID-token access to UserInfo. Missing user-key binding and audience rules remain unresolved design requirements, rather than a demonstrated failed guarantee. Minor is based on this documented dependency and the source’s explicit extension scope.

Local correction supported by the check. Separate ID-token validation from UserInfo retrieval using an access token. Identify any ID-token introspection or custom delegation-verification endpoint as an extension, with its authentication and authorization requirements. This correction was checked against standards; no complete repaired implementation was built or tested.

# 4. Protocol requirements that remain Needs Evidence

User-signature binding (B.1, p.15). Hash references to an OP-issued user ID token and an Agent-ID token do not themselves identify the public key authorized to sign the separate delegation token. OIDC Core’s mandatory ID-token fields do not include an end-user public key. A concrete profile should bind the delegation-verification key to the authenticated user and specify how that binding is established and checked.

Counterevidence and limit. The manuscript’s requirement that the human user signs the delegation token can reasonably presuppose an authenticated user key. Customized registration or an additional credential can provide it. The paper does not present a complete validator accepting arbitrary keys, so this review does not manufacture an impersonation attack by assuming such an implementation.

Audience and cross-service use (B.1-B.3, pp.15-16). Standard ID-token validation requires the relying party’s client identifier to appear in the token audience. Shared trust in the OP alone does not make a token issued to one client a valid login token for any other client. The delegation profile needs defined audiences, issuer trust and permitted cross-service verification semantics.

Counterevidence and limit. Purpose-built delegation credentials, suitable audience values or token exchange can supply a valid design. Wrapping a token in another credential does not by itself explain those rules, but an incomplete profile is not evidence that a deployed verifier disables audience checks.

Further implementation boundaries. A deployable system also needs enforceable scope semantics, replay and freshness handling, revocation behavior and rules for delegation across agents. The manuscript names validity/revocation information and describes a threat model; this review did not verify an implementation or formal security proof. The conditional threat-mitigation discussion in B.5 should be read at that proposal-level resolution.

# 5. Scoping: explicit limitations and positive evidence

Section 4.1, p.6, proposes translation to structured resource policies followed by human review, and expressly defers validation and robustness evaluation. Section 5.1 and Appendix D.2, p.20, acknowledge mistranslation, fallible human review, prompt-injection-driven privilege expansion, contextual drift and dependence on third-party enforcement. These limitations are already disclosed and are not recast as new demonstrated defects.

The cited IBAC-DB work describes generation of PostgreSQL permission rules from natural-language intent. The cited RAGent work describes retrieval-assisted construction of structured JSON access policies. Inspection of the primary papers supports feasibility of those specific approaches; it does not establish universal semantic fidelity for arbitrary instructions, resources or downstream services. The present paper does not provide a universal translation-soundness theorem.

Inter-agent scoping (C.7, p.19) describes forwarding scope, obtaining a structured interpretation, and approval by a user or another agent. It does not supply a formal semantic subset test proving that every downstream permission is contained in the original authorization. This is a remaining verification requirement. The disclosed translation and enforcement assumptions prevent treating an arbitrary mistranslation scenario as a newly demonstrated failure of a claimed complete attenuation algorithm.

Structured permissions constrain actions only when the relevant access paths are actually mediated by their enforcement mechanism. They do not certify the truth of model capability claims, good intentions, correct reasoning or task success inside an authorized resource boundary. The illustrative examples in Appendix E should remain conditioned on the proposed enforcement and policy assumptions.
