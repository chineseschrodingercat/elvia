Abstract: Two implementation defects affect the released Fleet of Agents system’s central cost and selection mechanisms. Merging several physical API responses discards all but one request’s input-token usage; a finite example understates the applicable usage-based cost by 44.05%. The WebShop evaluation path uses the action-generation newline stop and a whole-response substring parser, so valid evaluator explanations can reverse the intended state ranking. Both findings have Major scope for the affected released implementation. Neither identifies the exact code or billing records behind the published experiments. Several reported numerical comparisons and data splits are also checked, with counterevidence and unreproduced empirical claims kept explicit.

# Claims, definitions, and dependencies

FoA maintains a population of agents, advances each by mutation, evaluates states, and resamples promising states, with optional backtracking to earlier states. Caching and grouping identical prompts are intended to improve the cost–quality trade-off. These are the operative claims in Sections 3–6, the extended algorithm on pp. 13–16, and Appendix C.

Equation reference: eq:cost. A logical group asks for several completions of one prompt. A physical request is one successful call to the provider. The distinction matters when a provider adapter splits a logical group. Let request \(j\) report \(P_j\) input tokens and \(O_j\) output tokens. Under the stated usage-based prices \(r_{\rm in}\) and \(r_{\rm out}\), in dollars per million tokens, the applicable cost is \[
 C=\frac{r_{\rm in}\sum_jP_j+r_{\rm out}\sum_jO_j}{10^6}.\] This expression assumes that each request’s reported tokens are billable at those rates. It is not a claim about a provider’s present-day discounts or an unseen invoice.

For WebShop, the evaluator prompt asks for an explanation followed by a final correctness score \(s\in\{1,\ldots,10\}\). The released implementation maps this to a value in \([0,1]\), caches it, and uses values in selection. Thus both the completeness of the evaluator response and the extraction of its final score are dependencies of the main coordination mechanism.

# Problem 1: physical request usage is lost when responses are merged

## Source claim and suspect step

Appendix C.3, p. 26, attributes a batching saving to paying for the common input once while obtaining multiple outputs. A single physical multi-completion request can have precisely that property. The released adapter, however, also merges multiple physical requests.

In `async_engine/api.py`, `together_request` (starting at line 252) sets `max_n=16`, partitions \(n>16\), calls the provider separately for each part, and then invokes `merge_responses`. The Groq adapter similarly makes \(n\) separate requests with one completion each. In `utils.py`, lines 738–773, `merge_responses` retains the first response’s input-token count and adds subsequent output-token counts, but explicitly adds zero to input-token usage. The ordinary `API.request` accounting then receives this merged usage. The experiment drivers use |api.cost(tab_name=...)| to record costs; a tab labels accounting and does not restore discarded physical usage.

Consequently, the saved ordinary usage estimate can represent an idealized shared-input call rather than the calls actually made. The relevant failure is not that batching itself is invalid, but that its physical-request boundary is removed from the accounting.

## Complete finite check

Equation reference: eq:loss. Take a permitted logical request for \(n=27\) completions. The Together adapter splits it into 16 and 11. Suppose each physical response reports \(P=1000\) input tokens and each completion uses 10 output tokens. There are two successful physical requests and \(270\) total output tokens. The released catalog’s Llama-3.2-90B rates used in this fixture are \(r_{\rm in}=r_{\rm out}=1.2\) dollars per million tokens. Equation [eq:cost] (#eq:cost) gives \[C_{\rm physical}
 =1.2(2000+270)/10^6
 =0.002724\ {\rm dollars}.\] The merge rule instead yields \[C_{\rm recorded}
 =1.2(1000+270)/10^6
 =0.001524\ {\rm dollars}.\] The undercount is \(0.001200\) dollars, or \(44.0529\%\) of the applicable physical-request cost. No retries, failed calls, or model-quality assumptions enter this example. For \(q\) identical-prompt physical requests, each with \(P\) billable input tokens, the missing amount is exactly \[
 \Delta C=(q-1)P\,r_{\rm in}/10^6.\]

The cardinality is supported by the released interface rather than an out-of-range synthetic call. The Game of 24 driver sets evaluation batch size to \(3N\), while the agent evaluator requests three judgments per state. Appendix C.4 uses \(N=9\). A group of 27 identical evaluation prompts is therefore possible when the population contains the same state, which resampling and cloning permit. The example proves a reachable accounting defect; it does not establish how often such a group occurred in the unpublished runs.

## Counterevidence and precise limits

If a logical group is handled by one physical request, retaining its one input-token count is appropriate. The OpenAI single-call route is not subject to this particular multi-call loss. Smaller groups, differing prompts, cache hits, or different provider charging rules can reduce or remove the example’s effect. The source snapshot need not be the historical experimental version. Neither the paper’s total token logs nor provider invoices are available to determine the frequency or aggregate magnitude.

A related unresolved version question is that Table 5, p. 19, lists a Llama-3.2-90B output rate of \(0.06\), whereas the reviewed code catalog uses \(1.2\) per million. The ratio is 20, but the relevant historical price and the rate used for each published result have not been established. That discrepancy is Needs Evidence; it is not substituted for the demonstrated merge defect or used to calculate a corrected published table.

## Core impact, severity, and bounded correction

Dollar cost is a central comparison axis and part of the paper’s principal efficiency claim. Dropping physical input usage directly changes that axis for the supported execution path. The finding is Major for the released cost-measurement implementation. It does not establish that every reported cost is wrong, that a quality ranking reverses, or that the overall coordination idea fails.

A precise repair is to retain and sum usage for every physical request under an explicit pricing model, and to report any hypothetical shared-input cost separately. Summing both responses restores \(0.002724\) in the fixture and, by additivity, restores [eq:cost] (#eq:cost) for the stated model. Provider discounts, cached-token classes, retries, and invoice reconciliation need their own recorded rules. No source patch or historical rerun was performed, and author adoption has not been requested.

# Problem 2: the WebShop evaluator does not implement its stated score interface

## Claim, configuration, and parser

Table 6, p. 19, distinguishes the WebShop action-generation stop sequence `["\n"]` from the evaluation setting `null`. Prompt 7 on pp. 23–25 asks for analysis and a final line of the form Thus the correctness score is \(s\).

The driver `run/webshop.py`, lines 32–62, defines both configurations but constructs one `API` with `step_api_config`. Its action and evaluation batchers both receive that instance (lines 131–132). The evaluation configuration is not supplied to the actual call; changing the accounting tab to `eval` does not change the API configuration. Thus the evaluator inherits the action’s newline stop and may lose the final score line.

There is a second, independent failure at `src/agents/ws.py`, |value_outputs_unwrap|, lines 197–219. The parser searches the entire reply for `"10"`, then `"9"`, down to `"1"`, returning the first match divided by ten. It does not locate the score declaration. Digits in prices, quantities, or the explanation can become the state value even without truncation.

## A valid-response counterexample

Consider two evaluator responses whose intended scores obey the required range and final-line format:

> A: The item costs 100 dollars, exceeding the budget.
> Thus the correctness score is 1

> B: The task is not yet complete.
> Thus the correctness score is 9

The numerical values specified by the final lines are \((0.1,0.9)\). With the full replies, the released substring rule returns \((1.0,0.9)\), because `100` contains `10`. If the newline stop truncates each reply to its first line, the same rule returns \((1.0,0.0)\): A contains `10`, and B contains no digit. Thus one defect persists when the other is removed.

For two equal-age candidate states and ideal linear weighting, the intended probability of selecting A is \(0.1/(0.1+0.9)=0.1\). The full-reply parser instead gives \(1/(1+0.9)=10/19\), about \(0.5263\). The driver adds \(10^{-6}\) to retained weights; including it changes the two probabilities only to approximately \(0.1000008\) and \(0.5263158\). With truncation, B is assigned zero; the driver excludes newly evaluated zero-valued states from its retained records. With no other retained state, A is selected with probability one. If zero-valued states were retained instead, the epsilon-smoothed probability would still be approximately \(0.999999\).

All assumptions are explicit: ordinary nonterminal WebShop states, a valid one-to-ten evaluation, an explanation containing an ordinary price, no previous cached evaluation, equal age for the comparison, and the driver’s linear resampling path. No claim is made about the probability that a particular model emits these exact sentences. The interface must correctly handle them if its final-line score contract is to hold. The independently written parser and configuration fixtures are saved with the review.

## Counterevidence and alternative interpretations

A model can sometimes place its score before the first newline or omit digits from the explanation, in which case this fixture’s failure may not occur. Such outputs do not repair an interface that explicitly permits analysis before the final score. The implementation might also differ from the one used for the historical tables. The comment above the parser attributes it to LATS; this review reproduces the defect in the supplied FoA snapshot and makes no first-discovery claim about that code pattern.

This check does not show that the environment reward or the final success indicator is directly parsed by this function. The established path is evaluator value, caching, and resampling. A system can retain substantial benchmark success despite erroneous selection weights. Those facts limit the empirical conclusion but do not remove the algorithmic dependency.

## Core impact, severity, and correction

Evaluation-guided selection is part of FoA’s defining coordination mechanism. The implementation can invert the evaluator’s expressed preference and discard the higher-scored state. This is Major for the released WebShop evaluation path. The source evidence does not identify how much the published WebShop score would change after correction.

Use the evaluation configuration for evaluation calls and extract a validated final score with an anchored grammar or a structured response. A missing score should be distinguished from a genuine zero-valued state. An independently written anchored final-line extractor returns \((0.1,0.9)\) for the complete replies above. It cannot recover a score that was never received, so fixing the parser alone is insufficient. These statements verify a narrowly specified interface repair, not a repaired benchmark or a deployed author implementation.

# Additional checked claims and counterevidence

The four main comparisons in Section 5 and Figure 4 were recalculated from the displayed aggregate values. The quality increases are \(2.0,4.8,9.5,1.7\) percentage points, averaging \(4.5\), compatible with an approximately five-point summary. The corresponding FoA-to-comparator cost ratios average approximately \(0.35749\), supporting an approximately \(35\%\) cost summary for those four selected comparisons. That computation does not establish the same average over every model–task combination.

Two local percentage statements need clarification. The change from \(75.02\) to \(62.93\) dollars is a \(16.12\%\) reduction relative to \(75.02\), not \(25\%\); the SciBench ratio \(0.80/5.11\) is \(15.66\%\), not \(14\%\). These are bounded arithmetic inconsistencies in the displayed-value narrative. They do not change the shown order of those methods or supply an additional core failure.

The Game of 24 and crosswords test/validation indexing in the inspected data module agrees with the paper after converting zero-based indices to the paper’s one-based convention. The WebShop test set agrees. The released validation range contains ten tasks (55–64), whereas the paper states fifteen (55–69); historical tuning provenance is unresolved. The paper discloses single-run GPT-4 results, and five trials for the other models. Aggregate means alone do not establish paired significance or a universal improvement; no such test was fabricated here.

Uniform resampling need not preserve every distinct state, but the paper says it may maintain diversity, not that it guarantees preservation. This candidate criticism is therefore rejected. The main method makes no formal convergence or global optimality theorem requiring a newly invented guarantee. The appendix explicitly discusses the RAFA score comparison and its metric differences; that disclosed distinction is not relabeled as an undiscovered error. Ablation trends and figure context were read, but raw trajectories, all plotted numerical coordinates, and independent runs were unavailable.

No verified later-version correction or author erratum was found in the supplied version-bound materials. No exhaustive external erratum search is claimed. Establishing the effects of either main Problem on the published tables requires the historical commit, requests and responses, usage/pricing records, and a controlled rerun.
